# DistriCompute-Distributed — Implementation Plan

Each phase ends with the same steps: build, run the tests, review, fix defects, update the documentation, and
commit only completed work. The status table records what has actually been done. It is never filled in ahead
of time.

## 1. Phases, deliverables and acceptance criteria

| Phase | Deliverables | Acceptance criteria |
|---|---|---|
| **1. Inspect and agree on contracts** | Repository inspection; [architecture](architecture.md); this plan; draft [integration contract](integration-contract.md); Maven module building against Core; CI workflow | `./mvnw -f distributed/pom.xml verify` passes from a clean checkout after Core is installed; CI runs the build and each test group as separate steps |
| **2. Protocol and worker registration** | Envelope and 11 message types; payload records; protocol version rules; framing with size limits; validation; duplicate-message filter; HMAC registration proof; [network-protocol.md](network-protocol.md) | Round trip of every message type; malformed, oversized, truncated, unknown-type and wrong-version input rejected with specific codes; forged or replayed registration proofs rejected |
| **3. Coordinator and registry** | TCP server, connections with bounded queues, registration handshake, `WorkerRegistry` with capabilities, status, load and history, control loop | Real sockets: a client registers, is acknowledged and listed; duplicates, bad credentials and pre-registration messages are rejected; disconnection updates the status |
| **4. Worker execution with Core** | `WorkerNode`: configurable identity, coordinator address, limits; capability detection; bounded executor running Core `PartitionWorker`; progress; results; heartbeats; graceful shutdown; reconnection | A worker process registers real capabilities, executes a Core work unit received over TCP and returns a result that Core accepts |
| **5. Dispatch and result collection** | Tasks, partitions and attempts; bounded pending queue; dispatcher; acceptance and rejection; result metadata validation; duplicate detection; completion through Core | Coordinator plus 1 and 3 workers run every distributable built-in algorithm; results equal the sequential digest |
| **6. Scheduling policies** | Eligibility rules; round robin, least loaded, capability-aware, performance-aware and dynamic policies; decision records; [scheduling.md](scheduling.md) | Unit tests of each policy's choice on constructed worker states; every assignment records worker, task, policy, worker state, explanation and time |
| **7. Heartbeats and recovery** | Heartbeat monitoring (suspect, unavailable); task timeouts; failure classification; retry policy with attempt ids; quarantine; coordinator shutdown; [fault-tolerance.md](fault-tolerance.md) | Fault tests: disconnect, missed heartbeats, task timeout, invalid result, duplicate result; retried tasks complete with the correct result; exhausted retries fail clearly |
| **8. Metrics and events** | Attempt and task metrics separating computation, communication and scheduling; worker utilization and load distribution; event model and bus; HTTP API with Server-Sent Events | Metrics present and consistent in integration tests; events observed in order; HTTP endpoints tested over real HTTP |
| **9. Fault simulation** | Explicitly enabled fault profiles on workers (disconnect, hang, delay, latency, slowdown, corrupt or duplicate results, capacity changes); coordinator opt-in for such workers | Each fault produces the documented runtime reaction in a test; fault workers are rejected unless the coordinator allows them |
| **10. MPI demonstrations** | C programs: point-to-point, broadcast, scatter, gather, parallel computation; Makefile; run script; README | Built and run with a real MPI implementation, locally and in CI |
| **11. Application integration** | Java facade for embedding; strategy advice with runtime resources; manual overrides recorded; integration contract complete | Integration test drives the facade the way the Application would; contract examples generated by real runs |
| **12. Tests, documentation, release** | Multi-process tests; local multi-worker demonstration; deployment guide; benchmarks with real measurements; implementation report | All test groups pass locally and in CI; documentation matches the code |

## 2. Status

| Phase | Status | Notes |
|---|---|---|
| 1 | Done | Repository inspected (one repository, one branch per component; Core complete on `feature/core-engine`). Layout decided: `distributed/` on a branch based on Core. Architecture, plan and draft integration contract written. Maven module builds against Core with the same quality gates (`-Xlint:all -Werror`, Checkstyle, SpotBugs, JaCoCo); runnable jar; CI workflow. |
| 2 | Done | Envelope with 11 message types and payload records; Core `WorkUnitMessage`, `PartialResultMessage` and `ErrorInfo` embedded unchanged; id and protocol-version rules; codec that classifies malformed, unknown-type, wrong-version, invalid-envelope and invalid-payload input; newline framing with size limits and partial-read reassembly; duplicate-message filter; mutual HMAC-SHA256 registration proof with replay protection. 37 tests pass. The framing tests found an off-by-one in the size limit, which was fixed. |
| 3 | Done | `Coordinator` with a TCP (optionally TLS) accept loop; `Connection` with reader and writer threads and a bounded outbound queue; single-threaded control loop owning all state; registration handshake (proof verified on the connection thread, policy on the loop: duplicate ids, worker limit, fault-simulation opt-in); `WorkerRegistry` with capabilities, status, load, counters and performance history kept across reconnections; heartbeat acknowledgement, `SUSPECT` and heartbeat-timeout disconnection; protocol enforcement (pre-registration messages, wrong direction, impersonation, duplicates, malformed and oversized frames, wrong versions, registration timeout, error budget); `coordinator` CLI command with properties files. 66 tests pass, including 18 over real loopback TCP (2 with TLS certificates made by keytool); the registration suite passed 5 consecutive runs. |
| 4 | Done | `WorkerNode`: configurable identity, coordinator address, limits, labels and algorithm allow list; capabilities detected from the JVM and Core's registry (GPU only if Core detects a backend); registration with mutual proof; heartbeats on their own thread with coordinator-silence detection; admission (shutdown, duplicate attempt, unsupported algorithm, memory, capacity) with retryability; execution through Core `PartitionWorker` on a fixed platform-thread pool; throttled progress; attempt timeouts; cooperative cancellation; reconnection with exponential backoff and jitter; graceful drain and abrupt abort; capacity changes at run time; `worker` CLI command. 80 default tests pass, including results accepted by a Core session and bitwise equal to sequential, and a multi-process test with separate worker JVMs (one stopped with SIGTERM, one with SIGKILL). |
| 5 | Done | Distributed tasks, partitions and attempts (ids `<partitionId>/a<n>`) on the control loop; Core sessions opened off the loop; bounded priority queues with dynamic assignment as slots free up; eligibility (status, algorithm and version, memory, message size, free slot, soft exclusion of workers that failed a partition, worker limit) and the least-loaded policy (others in Phase 6); encoding off the loop; acceptance, progress, results classified by Core (accepted, duplicate, late, conflicting, invalid), worker-reported failures and refusals, retry budget, clear failure when retries are exhausted; completion through Core aggregation and verification; cancellation propagated to workers; `DistributedMetrics` separating computation, communication and scheduling. All 10 distributable Core algorithms complete on 1 and on 3 real workers, 8 bitwise equal to sequential and 2 (floating-point reductions) verified within rounding. A scripted worker sends duplicate, corrupted, foreign and unknown results. Two races found by tests were fixed: the worker freed its slot after sending the result (spurious refusal), and a stopped worker could still be handed a task. 90 default tests pass, plus the process test. |
| 6 | Done | Round robin, least loaded, capability-aware (idle cores, memory headroom), performance-aware (observed kernel throughput and transfer rate, exploration of unmeasured workers) and dynamic (longest-waiting worker) policies behind one `SchedulingPolicy` interface; eligibility rules with recorded reasons; decision records on every attempt; default policy changeable at run time; [scheduling.md](scheduling.md). 9 unit tests on constructed worker states; every policy completes a 12-partition task on 3 real heterogeneous workers with an explanation on every assignment. 106 default tests pass. |
| 7 | Done | Explicit `RetryPolicy` and `FailureKind` (which failures count against the attempt budget); coordinator-side attempt timeouts with `CANCEL`; acceptance timeout; task deadlines; heartbeat reconciliation (attempts missing from a heartbeat are lost); quarantine after repeated invalid results, with the quarantined worker's running attempts moved elsewhere; no-capable-worker timeout with per-worker reasons; [fault-tolerance.md](fault-tolerance.md). 12 fault tests (crash mid-task, missed heartbeats, hung attempt, lost attempt, unconfirmed attempt, quarantine, deadline, no capable worker, late-joining worker, graceful drain, coordinator shutdown with reconnection, exhausted retry budget) pass 5 consecutive runs in about 13 s; 108 default tests pass. Writing them exposed a gap: a retry sent back to a worker that never confirmed it would have waited for the full 10-minute attempt timeout. The acceptance timeout and quarantine rescheduling close it. |
| 8 | Done | Event model with 19 types and global sequence numbers; non-blocking `EventBus` with history, replay, per-subscriber bounded queues and drop notices; events from workers, tasks, attempts, retries and policy changes; `CoordinatorMetrics` (workers per status, slots, tasks, attempts, retries, bytes); HTTP API on the JDK server (JSON resources, task submission, cancellation, policy, catalog, events, Server-Sent Events, bearer token, CORS). 119 default tests pass 3 consecutive runs; 12 fault tests pass. These tests found four defects, all fixed: `AGGREGATING` was never reported; worker-reported failures produced no event and no failure count; a drop notice was lost if publishing stopped; and a race let a heartbeat built before an acknowledgement be sent after it, so a running attempt looked lost. For that race, heartbeats are now built atomically with acknowledgements, and the coordinator requires two consecutive omissions. |
| 9 | Done | `FaultProfile` and deterministic `FaultInjector` (per-attempt behaviour drawn from seed and attempt id): slowdown, response delay, link latency, disconnection after N tasks, stopped heartbeats, hanging, failing, corrupting and duplicating attempts, capacity schedule; enabled only by an explicit profile, reported as `faultSimulation`, refused by coordinators without the opt-in; example profiles; documentation. 10 fault-simulation tests with real workers pass 3 consecutive runs. Writing them exposed a flaw in soft exclusion: a worker that had already failed a partition was used again whenever the healthy workers were only busy, which let an always-failing worker exhaust the retry budget. Fixed: a busy capable worker is now waited for. |
| 10 | Done | Four C programs ([mpi/](../mpi)): point-to-point (ring and ping-pong with latency and bandwidth), broadcast (`MPI_Bcast` against linear sends), scatter and gather (`MPI_Scatterv`, `MPI_Gatherv`, `MPI_Reduce` with uneven chunks), and parallel prime counting (`MPI_Reduce`, checked against known π(n)). Each exits non-zero on any mismatch. Makefile (`-Wall -Wextra -Werror`), run script (one machine or a hostfile), README with a real run and an honest reading of it, comparison with the Java runtime, and a CI job. Built and run with Open MPI 4.1.6 using 2, 3 and 4 processes; every check passed. |
| 11 | Done | Java facade completed for embedding: `advise` (Core's `StrategyAdvisor` fed with the eligible workers as Core resource nodes, the measured network, and calibrations from the Application or measured by the runtime), `addCalibrations`; `SEQUENTIAL_CPU` and `MULTITHREADED_CPU` run on the coordinator through Core's `LocalExecutionEngine` with the same snapshots and events; `GPU` and `HYBRID` refused with an explanation; manual overrides recorded in the snapshot and as a `STRATEGY_OVERRIDE` event; HTTP `POST /advice`, `GET`/`POST /calibrations`, `overrideReason`; `submit`, `advise` and `status` command-line clients; integration contract completed, with a Spring Boot embedding sketch (not compiled here: the Application repository was not available). `ApplicationIntegrationTest` drives the facade the way the Application would. 125 default tests and 23 fault and process tests pass. ## 3. Postponed features

| Feature | Reason |
|---|---|
| GPU and hybrid execution | Core has no GPU backend. Workers report GPU as unavailable, and the runtime rejects these modes with an explanation. |
| Coordinator persistence and fail-over | The first release has one coordinator. After a restart, workers re-register automatically, but in-flight tasks are lost and reported. |
| Binary payload frames | Base64 in JSON is simpler to inspect and debug. The measured overhead decides whether binary frames are worth it. |
| Work stealing and uneven partition sizes | Core plans equal partitions. Over-decomposition plus dynamic dispatch gives load balancing without changing Core. |
