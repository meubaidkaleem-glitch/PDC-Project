# DistriCompute-Distributed — Implementation Plan

Each phase ends with the same steps: build, run the tests, review, fix defects, update the documentation, and
commit only completed work. The status table records what has actually been done. It is never filled in ahead
of time.

## 1. Phases, deliverables and acceptance criteria

| Phase | Deliverables | Acceptance criteria |
|---|---|---|
| **1. Inspect and agree on contracts** | Repository inspection; [architecture](architecture.md); this plan; draft [integration contract](integration-contract.md); Maven module building against Core; CI workflow | `./mvnw -f distributed/pom.xml verify` passes from a clean checkout after Core is installed; CI runs the build and each test group as separate steps |
| **2. Protocol and worker registration** | Envelope and 11 message types; payload records; protocol version rules; framing with size limits; validation; duplicate-message filter; HMAC registration proof; [network-protocol.md](network-protocol.md) | Round trip of every message type; malformed, oversized, truncated, unknown-type and wrong-version input rejected with specific codes; forged or replayed registration proofs rejected |
| **3. Coordinator and registry** | TCP server, connections with bounded queues, registration handshake, `WorkerRegistry` with capabilities, status, load and history, control loop | Real sockets: a client registers, is acknowledged and listed; duplicates, bad credentials and pre-registration messages are rejected; disconnection updates the status |
| **4. Worker execution with Core** | `WorkerNode`: configurable identity, coordinator address, limits; capability detection; bounded executor running Core `PartitionWorker`; progress; results; heartbeats; graceful shutdown; reconnection | A worker process registers real capabilities, executes a Core work unit received over TCP and returns a result that Core accepts |
| **5. Dispatch and result collection** | Tasks, partitions and attempts; bounded pending queue; dispatcher; acceptance and rejection; result metadata validation; duplicate detection; completion through Core | Coordinator plus 1 and 3 workers run every distributable built-in algorithm; results equal the sequential digest |
| **6. Scheduling policies** | Eligibility rules; round robin, least loaded, capability-aware, performance-aware and dynamic policies; decision records; [scheduling.md](scheduling.md) | Unit tests of each policy's choice on constructed worker states; every assignment records worker, task, policy, worker state, explanation and time |
| **7. Heartbeats and recovery** | Heartbeat monitoring (suspect, unavailable); task timeouts; failure classification; retry policy with attempt ids; quarantine; coordinator shutdown; [fault-tolerance.md](fault-tolerance.md) | Fault tests: disconnect, missed heartbeats, task timeout, invalid result, duplicate result; retried tasks complete with the correct result; exhausted retries fail clearly |
| **8. Metrics and events** | Attempt and task metrics separating computation, communication and scheduling; worker utilization and load distribution; event model and bus; HTTP API with Server-Sent Events | Metrics present and consistent in integration tests; events observed in order; HTTP endpoints tested over real HTTP |
| **9. Fault simulation** | Explicitly enabled fault profiles on workers (disconnect, hang, delay, latency, slowdown, corrupt or duplicate results, capacity changes); coordinator opt-in for such workers | Each fault produces the documented runtime reaction in a test; fault workers are rejected unless the coordinator allows them |
| **10. MPI demonstrations** | C programs: point-to-point, broadcast, scatter, gather, parallel computation; Makefile; run script; README | Built and run with a real MPI implementation, locally and in CI |
| **11. Application integration** | Java facade for embedding; strategy advice with runtime resources; manual overrides recorded; integration contract complete | Integration test drives the facade the way the Application would; contract examples generated by real runs |
| **12. Tests, documentation, release** | Multi-process tests; local multi-worker demonstration; deployment guide; benchmarks with real measurements; implementation report | All test groups pass locally and in CI; documentation matches the code |

## 3. Postponed features

| Feature | Reason |
|---|---|
| GPU and hybrid execution | Core has no GPU backend. Workers report GPU as unavailable, and the runtime rejects these modes with an explanation. |
| Coordinator persistence and fail-over | The first release has one coordinator. After a restart, workers re-register automatically, but in-flight tasks are lost and reported. |
| Binary payload frames | Base64 in JSON is simpler to inspect and debug. The measured overhead decides whether binary frames are worth it. |
| Work stealing and uneven partition sizes | Core plans equal partitions. Over-decomposition plus dynamic dispatch gives load balancing without changing Core. |
